Context

Phase 7 (read path) is done and merged to main (PR #15, commit f99cb0e). This plan covers Phase 8 per docs/PROJECT_ROADMAP.md: the add-spot form (NewSpotCard) actually persists to Postgres via a Zod-validated POST /api/spots, wired through a TanStack Query useMutation that invalidates the spots query on success so the map refetches without a manual reload.

Work is on branch AC-1011 (branched from main, no Phase 8 commits yet).

Two real bugs surfaced while reading the current code for this plan — both are fixed as part of doing Phase 8 correctly, not optional cleanup:

1. src/types/spot.ts's Spot.ownerId is typed number, but prisma/schema.prisma defines ownerId String? (references User.userId, a UUID) — a type mismatch. NewSpotCard.tsx currently sends a hardcoded ownerId: 0 in its onSave payload, which matches neither. No sign-in flow exists yet (Phase 13+), so per CONTEXT.md's Owner definition ("a Spot created while signed out has no owner"), ownerId should be omitted/undefined for now, and the type fixed to string.
2. (pre-existing, not fixed, flagged again) FilterBar.tsx's matchesFeature (~line 23) is always false for a spot with zero Features — a spot saved with no Spot Features checked silently never renders under any filter. First caught during Phase 7's manual verify. Not this phase's job unless it actively gets in the way of verifying Phase 8 — if it does, flag it rather than quietly fixing it.

Also note: NewSpotCard's form has no city input, so city: "" is always sent. The Zod schema needs a deliberate decision on this (treat empty string as valid for now — adding a real city field isn't Phase 8's job) rather than silently accepting it without anyone having decided that's fine.

4. POST /api/spots route handler (Alex writes)

Same file, src/app/api/spots/route.ts — add export async function POST(request: Request) alongside the existing GET.

- Parse request.json(), run it through the Zod schema's safeParse — don't throw straight from parse(), the route needs to branch on success/failure rather than crash.
- On failure: return NextResponse.json({ error: ... }, { status: 400 }). Shape of the error body (flattened Zod issues vs. a single message) is your call — just make it something the client can show.
- On success, write in two steps, mirroring the exact pattern prisma/seed.ts already uses for this same geography-column problem (Spot.latLng is Unsupported("geography(Point, 4326)"), so Prisma Client's normal create() can't set it):
  1. prisma.spot.create({ data: { ...everything except latLng } }) — gets back the real autogenerated id, spotId, createdAt.
  2. A follow-up prisma.$executeRaw UPDATE "Spot" SET "latLng" = ST_SetSRID(ST_MakePoint(lng, lat), 4326) WHERE "id" = ${created.id} — same shape as seed.ts lines ~66-70.
- Reshape the result into the Spot JSON shape (spotId → id, plus the lat/lng you already have from the input — no need to re-SELECT) and return it via NextResponse.json(spot, { status: 201 }).

Done when: a POST with a valid body creates a real row (check Prisma Studio) and returns 201 + the new Spot; a POST with an invalid body returns 400 and writes nothing.
