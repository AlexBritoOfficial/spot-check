01

What "serialization" actually means

Concept
Keywordsserializationdeserializationwire shape

What

A Spot lives in memory as a rich JavaScript object — it can hold a Date, nested objects, whatever. A network can't send an "object," only bytes, which for a web API means text.

How

In memory (server)
{ id: 1, created_at: Date }
→
Serialize → text
'{"id":1,"created_at":"2026-…"}'
→
Parse (browser)
{ id: 1, created_at: "2026-…" }

In JavaScript this pair is JSON.stringify() (object → text) and JSON.parse() (text → object).

Why

Serialization is turning an in-memory object into flat text; deserialization (parsing) rebuilds an object from it on the other end. Your API does the first; TanStack Query does the second for you in Phase 7.

The one law of UI-first: a mock Spot must look exactly like the object that comes out of JSON.parse() on the client — not the object that existed on the server before serialization. Those two are not the same, and Chapters 03–04 are where they differ.
Idea to consider
This is why mock data is only useful if it's shaped like the wire, not like your ideal in-memory model. A mock that's more "correct" than what the real API will actually send is a mock that lies to you the day you connect the real backend.
02

JSON's tiny type vocabulary

ConceptGotcha
KeywordsJSON typesundefined vs null

What

JSON only knows six value types. Everything in a Spot has to reduce to one of them, or it gets transformed / dropped on the way out.

How

JSON typeYour Spot fieldNote
stringname, city, created_atText in double quotes only
numberid, rating, lat, lngIEEE-754 double — Ch 05
booleanis_skateabletrue / false
nullan absent photoThe only "empty" — no undefined
arrayfeaturesOrdered list
objectlat_lngNested key/value
  • No Date — becomes a string (Ch 03).
  • No undefined — a key whose value is undefined is silently omitted entirely. This is why "optional" and "null" are different things (Ch 08).
  • No enums, classes, functions, Map/Set — flatten to plain objects or vanish.
  • No BigInt — JSON.stringify throws on it.

Why

JSON was designed as a minimal, language-agnostic text format — it deliberately doesn't try to represent every JS runtime type, only the shapes common to essentially every language's data structures.

Remember: "JSON is text with six shapes." Anything richer than those six is your responsibility to encode on the way out and rebuild on the way in.
Idea to consider
Try JSON.stringify({ a: undefined, b: null, c: new Date() }) in a console once. Watch a disappear, b stay, c turn into a string — that single line is this whole chapter, and it explains why "optional" (Ch 08) and "transformed" (Ch 03) are two completely different concerns.
03

Dates don't survive the trip

Bug-in-waitingConcept
KeywordsDate.toJSON()ISO-8601re-hydration

What

created_at is typed string, not Date — that looks odd at first (it is a date), but it's correct.

How

// before — in memory
{ id: 1, created_at: new Date() }

// after — JSON.stringify()
{ "id": 1, "created_at": "2026-08-02T14:30:00.000Z" }

Keep the transport type a string. Convert to a Date only at the moment you need date math or formatting, right where you use it:

const created = new Date(spot.created_at);   // re-hydrate on demand
created.toLocaleDateString();                // "8/2/2026"

Why

A Date object has a hidden .toJSON() method. When JSON.stringify hits it, it calls that method, which returns an ISO-8601 string. So by the time a spot reaches the browser, created_at is — and only ever was — a string. There is no Date on the client unless you rebuild one.

The honesty rule for mock data: because the real API sends a full ISO timestamp, mock created_at should be a full ISO string too — not a date-only string. A mock shaped differently from the API is a mock that lies, and the lie surfaces the day you swap in the real backend.
Idea to consider
This is the exact same lesson as Study Sheet 05, Item 5 (naming mismatches across a language/file boundary) wearing a different costume: a JS-native type (Date) simply doesn't exist on the other side of a serialization boundary. Any type richer than JSON's six needs an explicit, deliberate re-hydration step — it never survives by accident.
04

Location on the wire — the lat/lng order trap

ConceptGotcha
Keywordsnamed object vs. arraycoordinate order

What

lat_lng: { lat: number; lng: number } was chosen over two loose columns or a raw array — a small choice guarding one of the most bug-prone corners of the project.

How

ShapeLooks likeRisk
Two fieldslat: 42.3, lng: -71.0Location can get half-updated
Array[-71.0, 42.3]Which one is which?
Named object ✓{ lat: 42.3, lng: -71.0 }Self-documenting — chosen
ToolOrder it expects
Leaflet (Phase 3)[lat, lng] — latitude first
GeoJSON / PostGIS (Phase 6, 10)[lng, lat] — longitude first

Why

The database stores location as a PostGIS point, which serializes to plain numbers — the only question is order, and different tools disagree about it silently. Both values are just numbers, so nothing errors; your pin just lands in the wrong ocean.

Boston is lat 42.36, lng -71.06. Swap them and you get a point off the coast of Western Sahara — a bug that parses fine and points nowhere real. Naming the fields lat and lng means the order can never be ambiguous at the call site.
Idea to consider
Anywhere two independently-built tools have to agree on the meaning of a bare positional value (array order, argument order, column order), that agreement is exactly the kind of thing that silently drifts. A named field is cheap insurance against a whole category of "everything type-checks, nothing works" bugs.

05

id: number or string?

Concept
Keywordsprimary keyenumerability

What

id: number was chosen. A real fork in the road — it ripples into React key props, the /api/spots/[id] route, and the Prisma primary key.

How

number (auto-increment)string (cuid / uuid)
DB defaultserial / autoincrement()cuid() / uuid()
ReadabilityGreat — 1, 2, 3Opaque — clx1a…
Guessable?Yes — /spots/2 invites enumerationNo — practically unguessable
Made where?By the database on insertCan be made on the client too

Why

For a learning project, number is a perfectly good call — readable Prisma Studio rows, friendly URLs. The trade-off accepted: sequential ids leak "how many spots exist" and are trivially enumerable. If this ever went public with private data, that's when to revisit it.

Contract consequence: whatever you pick, mock ids must be that type. id: 1 and id: "1" are different contracts, and === comparisons in click handlers will care.
Idea to consider
The real axis isn't "which is more readable" — it's "who assigns this value, and when?" A database-assigned sequential id and a client-generatable uuid solve genuinely different problems (offline-first apps often need the latter, so an id can exist before the server has ever seen the record).
06

Union types as enums

Concept
Keywordsstring-literal unionruntime validation

What

Instead of typing spot_type: string, the exact allowed values are named directly.

How

export type SpotType = "park" | "street" | "diy";
export type Status   = "active" | "pending" | "closed";
export type Feature  = "ledge" | "rail" | "plaza" | "stairs" | "skatepark";

Why

A string-literal union turns a whole category of runtime bugs into compile-time errors. spot_type: "streat" (typo) is a red squiggle immediately, not a filter that silently matches nothing later. The editor also autocompletes the legal values.

This is a contract, not a convenience. A later filter comparing spot.spot_type === activeFilter is comparing against these exact strings, and the Postgres/Prisma enum must list the same values, character for character.

The watch-out: a union only guards code the compiler can see. Data arriving from the network is typed any until validated — a DB row with spot_type: "vert" would sail past TypeScript. That's exactly why runtime validation (e.g. Zod) exists: to re-check unions at the boundary the compiler can't reach.

Idea to consider
This is the compile-time half of the same exhaustiveness idea from Study Sheet 05, Item 2 (Record<K,V>) — a closed set of legal values, enforced by the type system. The gap it leaves (runtime data isn't automatically checked) is precisely the seam where a schema-validation library earns its keep.
07

spot_type vs. features — category vs. attributes

Pattern
Keywordscategory vs. attributedata modeling

What

The roadmap floated one flat list — park | street | ledge | rail | stairs | bowl | DIY. It was split into two dimensions instead.

How

spot_type — what KIND of place
"park" | "street" | "diy"
exactly one per spot
+
features — what's THERE
("ledge" | "rail" | "plaza" | …)[]
many per spot

Why

Those original values weren't the same kind of thing. "Street" is a category; "ledge" and "rail" are things a street spot has — and can have several at once. Cramming them into one field forces a false choice. This is the classic modeling question: "is this a single category, or a set of attributes?" Single category → one enum field. Set of independent traits → an array (or later, a related table).

The seam for later: this two-axis design maps naturally to the database — spot_type becomes an enum column, features becomes an array column or a related table. The flexibility is built in for free.
Idea to consider
This "one category vs. many attributes" question recurs everywhere in modeling — user roles vs. permissions, order status vs. order tags, a blog post's type vs. its labels. If you ever feel the urge to put the same value in both fields, that's the signal the two axes have blurred back together.
08

Optional fields = the nullability contract

ConceptGotcha
Keywordsoptional (?)nullable column

What

description? and photo? are optional; the rest are required. Each ? is a promise to the rest of the app: "this field might not be here — you must handle its absence."

How

On the wireIn TS after parseMeaning
key absentphoto === undefined"never set" — what ? models
"photo": nullphoto === null"explicitly empty" — DB NULL
"photo": ""photo === """set, to nothing" — a real string!
The mock uses photo: "". That's a present, empty string — a different case from the optional-and-absent that photo? describes. Pick one convention and make the mock and the API agree.

Why

Every optional field is a branch a component must write: {spot.photo ? <img …/> : <Placeholder/>}. Deciding nullability now, at the contract, is deciding how many of those branches exist. It also lines up with the database: an optional field is a nullable column; a required one is NOT NULL.

Idea to consider
Three states masquerading as "empty" (absent, null, "") is a very common source of subtle bugs in any typed system talking to an untyped wire format. Deciding — in writing, on purpose — which one your codebase means by "no value" heads off a whole class of "why doesn't my falsy check work" debugging later.
09

Naming consistency & type/data lockstep

Bug avoidedConcept
Keywordssnake_case vs camelCaseexcess property check

What

The shape briefly mixed conventions — spot_type, lat_lng, is_skateable in snake_case but createdAt in camelCase. It was unified on snake_case — and, crucially, changed in both the type and the data at once.

How

Deliberately rename one field in mock data but not the type, save, and read the two errors TypeScript gives (missing key + excess key). Fix the type. That error pair is the lockstep lesson.

Why

The type file and the mock file are two halves of one contract. Rename a field in the data but not the type, and TypeScript flags both: the object is missing a required old key and carries an unknown new one. That's the discipline — a shape change is never done until the type and every producer of that shape agree.

Why check the compiler at all: a clean tsc is the cheap proof that type and data still describe the same thing. Treat a green compile as a passing test of your data shape.

JavaScript's own convention is camelCase; snake_case keys are common in APIs and match SQL column names. Either is fine — consistency is the whole point. If Postgres columns end up snake_case and some JS wants camelCase, the translation happens in exactly one place: the serialization boundary (Ch 11).

Idea to consider
"Type and data move in lockstep" is a narrower instance of single source of truth (Study Sheet 05, Item 4) — the type file and the data file are two independently-editable places describing the same contract, and only the compiler is actually watching that they still agree.

One spot, three representations

Pattern
KeywordsDTOdomain entitydata model

What

"A skate spot" is not one thing in the codebase — it's the same concept wearing three different costumes depending on where it stands.

How

LayerName for itWhat it isLocation = ?
1. EntityDomain entityThe real ledge by the water. A concept, not code.a physical place
2. WireDTO / the Spot typeThe JSON the API sends & the UI renders.{ lat, lng }
3. StoreData model / schemaThe Prisma model & Postgres table it lives in.geography(Point)
 
// 2 · DTO (types/spot.ts) — the contract, Chapters 05–09
{ id: 3, name: "Copley Library", spot_type: "street",
  features: ["plaza"], lat_lng: { lat: 42.35, lng: -71.08 },
  created_at: "2026-08-02T…Z" }

// 3 · DATA MODEL (schema.prisma → Postgres)
model Spot {
  id         Int      @id @default(autoincrement())
  name       String
  spot_type  SpotType                          // Postgres enum
  location   Unsupported("geography(Point,4326)")
  created_at DateTime @default(now())           // timestamptz
}

Why

Confusing the layers is the root of most data bugs; separating them is most of software architecture.

Why UI-first works because of this: layer 2 (the DTO) is built first, by hand, against mock data. Layer 3 (the model) comes later and is shaped to match what layer 2 already promised — get the middle layer right and the bottom layer just conforms to it.
Idea to consider
This three-layer split (entity / DTO / persistence model) is one of the most transferable ideas in this whole manual — it's the same shape as MVC's model layer vs. its view-model, or a domain-driven-design "aggregate" vs. its database row. Once you can name which layer a piece of code is operating at, a lot of "where does this logic belong" confusion resolves itself.
11

The mapping — and where the transformation lives

ConceptGotcha
Keywordsimpedance mismatchroute handler

What

Every field either passes through unchanged or gets transformed as it crosses from the database (layer 3) to the wire (layer 2).

How

DTO field (Ch 05–09)Postgres / PrismaTransform?
id: numberInt @id @default(autoincrement())pass-through
name: stringString / textpass-through
spot_type: SpotTypePostgres enumsame values, different world
features: Feature[]text[] or related tablearray ↔ column/rows
lat_lng: {lat,lng}geography(Point,4326)real transform — Ch 04
created_at: stringDateTime / timestamptzISO string ↔ timestamp — Ch 03
description?: stringnullable textoptional ↔ NULL — Ch 08
DB row (layer 3)
location = POINT(-71.08 42.35)
→
Server route handler
reshape → { lat: 42.35, lng: -71.08 }
→
JSON to browser (layer 2)
matches the Spot type

Why

The transform happens neither in the browser nor the database — in the server route handler, the one place both worlds are visible at once. This gap between "how it's stored" and "how it's used" has a name: impedance mismatch. The server boundary's job is to absorb it, so the UI never sees a geography blob and the database never sees a JS Date.

The PostGIS reality check: Prisma can't fully model a geography column — it gets declared Unsupported(...) and read with a raw, parameterized query (ST_X/ST_Y). That's not Prisma failing; it's the exact seam where layer 3 refuses to auto-map to layer 2, and a person has to step in.
Idea to consider
For each row in the mapping table, the honest answer is always either "pass-through" or "transform" — and the three transforms here (location, date, optional/NULL) are precisely the three things earlier chapters drilled. That's not a coincidence: knowing what has to transform at a boundary is the whole reason to understand the layers in the first place.
A

Glossary

Serialization / deserialization
Turning an in-memory object into flat text for transport (JSON.stringify), and rebuilding an object from that text (JSON.parse).
Wire shape
The exact object shape that comes out of JSON.parse() on the receiving end — the only shape a client ever actually sees, regardless of what existed in memory before serialization.
String-literal union
A TypeScript type naming the exact legal string values ("park" | "street" | "diy") instead of the general string — compile-time enum-like safety.
Nullable column
A database column allowed to hold NULL — the storage-layer counterpart of a TypeScript optional (?) field.
DTO (Data Transfer Object)
The shape of data as it crosses a boundary (like an API response) — distinct from both the real-world entity it represents and the database model that stores it.
Impedance mismatch
The general gap between how data is stored (e.g. a relational/geographic database) and how it's used (e.g. a JS object) — something has to translate between the two.
B

Self-test

Say the answer aloud before opening each — the explaining is what makes it stick.

Why is created_at typed string and not Date?
Because JSON has no Date type. JSON.stringify calls Date.toJSON(), turning it into an ISO string — so by the time the UI sees it, it only ever was a string.
What happens to a key whose value is undefined when you JSON.stringify?
It's dropped entirely — the key doesn't appear in the output. A null value, by contrast, is kept.
Why is a named {lat,lng} object safer than [42.36, -71.06]?
Leaflet wants [lat, lng] but GeoJSON/PostGIS want [lng, lat] — opposite orders, both just numbers, so a swap fails silently. Named fields make the order unambiguous.
Why split spot_type from features instead of one flat enum?
Type is a single category (exactly one), features are independent attributes (many). One flat list forces a false either/or choice.
Name the three ways "no photo" can appear, and which one photo? describes.
Key absent (undefined) — what ? models; null (explicit empty); and "" (a present, empty string) — a different case from the first.
You rename a field in the mock but not the type. What does TypeScript say?
Two errors: the object is missing the required old key, and it carries an unknown excess key — type and data are one contract that must move together.
Name the three layers a single spot lives at.
Entity (the real place), DTO / the Spot type (the wire), and the data model (Prisma/Postgres). UI-first builds the middle layer first; the bottom one conforms to it later.
Which fields genuinely transform between database and wire, and where does that transform happen?
Location, created_at, and optional fields. The transform lives in the server route handler — the one place both worlds are visible.
